# 2026-11-05 장면 전환 준비 개선

## 변경

- `game.ts`: 이미지 요청을 공간 생성 대기열보다 먼저 시작한다. 플레이어 이동/추격 때문에 앞 공간의 생성이 대기하더라도 다음 공간 자료 요청은 시작한다. CPU/GPU 공간 생성은 한 번에 하나만 실행하며, 실제 이동 목적지가 대기 중인 다른 추측 공간보다 우선한다. `materials.prepareVisuals`의 중복 소스 보호용 이미지 배치 직렬화는 유지한다. 따라서 먼저 시작한 이미지 전송 자체를 다음 배치가 추월하는 기능은 아니다.
- 첫 집/첫 복도에서 연속 추격 동선인 24F 복도·계단·20F 복도를 앞서 준비한다. 이 준비는 승강기의 안전한 대기 때도 계속된다. 단, 저장에서 바로 승강기로 이어하는 경우에는 바로 다음 복도·공동현관만 요청해 짧은 구간에서 전체 추격 동선을 새로 생성하지 않는다. 신규 필수 시작 로딩은 추가하지 않았다. 안전한 공동현관/서고/B1 대기 구간은 옛 `chaseStages` 이름만으로 준비가 영구 차단되지 않는다. 실제/예정된 추격과 이동/드래그 중 무거운 생성은 계속 미룬다.
- 공간 입장 직후 500ms는 추측 공간 생성을 미룬다. 실제 목적지가 필요하면 이 유예를 기다리지 않는다. 텍스처마다 고정 16ms를 더하던 방식은 약 4ms 작업 예산마다 양보하는 업로드 배치로 바꿨다. 단일 이미지 업로드 자체는 분할할 수 없다.
- `ghost-hair.ts`: 동일한 머리카락의 초기 위상·색·가중치·인덱스 계산과 초기 정점 작성은 CPU 템플릿 하나에 보존한다. 각 귀신은 자신의 geometry/BufferAttribute/가변 배열/pose cache를 복사해서 사용한다. 템플릿은 렌더러에 연결되지 않는다.
- `ghost-tears.ts`: 동일한 원본 얼굴의 피눈물 부착점 탐색(126개 표본 × 4,650개 삼각형)을 재사용한다. 전체 원본 위치·인덱스를 비교하므로 다른 얼굴은 다시 계산한다. 움직이는 피눈물 geometry와 재질은 귀신별로 별도 소유한다. 캐시는 한 얼굴로 제한된다.
- 실제 대기/실패 표시와 재시도, 시간/추격/오디오 정지, 저장·이어하기 동작을 숨기거나 삭제하지 않았다. 종료 시 새로 분리한 모든 진행 중 준비 작업까지 기다린 뒤 GPU 자원을 정리한다.

## 머리카락/피눈물 캐시 단계의 CPU 생성 측정

같은 Mac의 Node22, 같은 순서로 실제 `buildWorld`를 세 번 호출한 프로파일용 fixture. Canvas 그리기 경계만 대체하며 WebGL/이미지 전송/셰이더 측정은 아니다. 각 프로세스의 첫 시도와 JIT 영향을 포함하며 독립적인 콜드 기기 3대 결과가 아니다. 전체 원본 로그를 보존했다.

CPU 프로파일에서 머리카락과 피눈물 초기 생성이 주요 반복 비용임을 확인한 후 캐시를 적용했다. 단순히 로딩 문구를 감추거나 동일 비용만 다른 시점으로 옮긴 변경은 아니다. 다만 공간 생성 전체는 아직 동기 작업이며 위 수치처럼 50ms 이상 작업이 남는다.

## 추가 불필요 작업 제거

- `sedan.ts`: 손상/운전석/조수석 접근의 boolean 조합별로 최대 8개의 CPU 전용 차량 템플릿을 보존한다. 차마다 geometry·material·Texture wrapper를 별도로 복제하고 차체 색만 적용한다. 매번 같은 곡선/튜브/법선/차체 지오메트리를 재계산하지 않는다. shader hook과 한 차 내부의 공유 관계를 보존하며, 한 차의 충돌 변형/문 포즈/폐기가 다른 차나 템플릿을 바꾸지 않도록 검사했다.
- `prologue.ts`: 최종 탈출 도로에는 절대 보이거나 포즈를 갱신하지 않는 도입 사고 여성의 전체 리그를 만들지 않는다. 기존 장면 조회용 이름의 빈 Group만 남긴다. 실제 조수석 귀신·트럭·첫 도입의 사고 여성은 유지한다.
- 주차장 자체 셰이더 준비는 유지한다. 이후 도로와 결합한 장면은 한 번만 컴파일한다. 기존 3/7/24초 포즈는 transform·uniform만 바꾸고, Three.js compile은 숨긴 메시까지 모두 순회하므로 같은 셰이더 집합을 세 번 컴파일할 이유가 없다. combined scene에 조수석·금 간 유리·빗물 유리·운전석 문이 실제 포함되는지 검사했다.

## 네이티브 WebGL 측정과 제한

Mac 잠금 때문에 최종 측정이 잠시 중단됐으나, 사용자가 확인한 뒤 지원되는 CUA 화면 조회로 접근 복구를 확인하고 재개했다. 잠금을 우회하지 않았다.

마지막 전후 비교는 동일한 최종 귀신 이동/출차 코드를 사용한다. 기준본에만 원래 streaming·hair·tears·sedan·prologue 생성 코드를 주입했다. Chrome foreground(`document.hidden=false`), viewport1920×817/DPR1, 실제 캔버스960×540, CPU 제한 없는 localhost Vite 소스 fixture와 production shader-diagnostic 설정을 사용했다. 배포 번들/네트워크 콜드 비교는 아니다. 브라우저/OS/드라이버를 재시작하지 않아 셰이더 캐시·GC 차이는 통제하지 못했다. 각 실행 후 Game.dispose를 기다리고 fixture 자신의 WebGL context를 명시적으로 해제했다.

정상 B1 저장 체크포인트를 이어한 뒤 5초 기다리고 실제 엔진의 전이 함수를 통해 주차장으로 들어간 1회씩의 측정이다. 사람의 전체 경로 걷기/장기 FPS와 구분한다.

| 마지막 주차장 비교 | 기준 | 최종 |
| --- | ---: | ---: |
| 진입 시 준비 대기 | 7338.6ms | 3.5ms |
| 실제 parking buildWorld 동기 생성 | 1078.6ms | 457.2ms |
| 추가 ending buildRoad 동기 생성 | 936.6ms | 666.8ms |

| 전체 관찰 구간 최대 프레임 간격 | 1200.9ms | 867.0ms |

**대기 시간을 크게 줄였고 실제 생성 비용도 줄였지만 멈칫을 완전히 없애지는 못했다.** 최종 후보에도 배경 준비 중 약0.87초 간격이 관찰됐다. 단일 이미지 GPU 업로드도 최대129.4ms였으며 큰 도로/공간 생성은 아직 동기 작업이다. 일부 비용은 안전한 선행 준비 시점으로 이동한다. “모든 챕터 렉 제거/모든 기기 무로딩”으로 보고하지 않는다. 느린 기기·자료 실패·매우 빠른 저장 복귀에는 정확한 대기/재시도 표시가 남는다.

보조 결과:
- 앞선 동일 foreground 첫 비교의 공동현관→서고는1296→2.4ms 대기였다. 이 비교 후 추가한 차량/최종도로 최적화와는 별도 단계다.
- 차가운 승강기 이어하기의 과도한 stairs/transfer lookahead는 회귀 검사 후 제거했다. 같은 최종 귀신 코드로 다시 비교한 경계 대기는4.3→2.4ms였고 최대 prefetch 간격은480.2→480.1ms였다. 이 역시 마지막 차량 캐시 적용 전의 보조 결과이며 최종 모든 공간 속도 보증으로 사용하지 않는다.
- 초기 숨긴 탭의 1초 타이머 제한, 잘못된 저장 stage, 다른 검사와 겹친 시행, 서로 다른 귀신 이동 코드가 섞인 프레임 비교는 최종 성능 근거에서 제외했다.

실제 built4173 smoke: 새로고침 후 메뉴 준비, 저장된24F 이어하기/재시도/3D 렌더, 한국어 설정과4개 언어 선택 항목, 실제 미션 메모 클릭·내용·일시정지 안내를 확인했다. 최종 생성기 수정 뒤 재빌드의 간단한 시작 확인은 상위 작업에서 추가한다.
